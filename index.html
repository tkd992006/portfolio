Product translation

외주개발과 창업을 하며 다양한 요구사항을 소프트웨어로 옮겨왔습니다.

외주개발에서는 고객이 설명한 요구사항을 화면, API, 데이터 구조로 정리해 납품했고, 창업에서는 문제 발견부터 제품 구현, 영업, 운영, 지표 확인까지 직접 부딪혔습니다. 음식점 식자재 발주, AI 스킨케어 상담, 내부 운영 도구, 모바일 웹앱처럼 사용 맥락이 다른 제품을 만들었습니다.

외주는 상대가 이미 가진 불편함을 정리해 납품 가능한 형태로 만드는 일이었고, 창업은 문제가 맞는지부터 계속 검증해야 하는 일이었습니다. 창업을 하면서 기능보다 유통, 영업, 운영까지 함께 봐야 한다는 감각이 생겼습니다.

먼저 사용자가 실제로 어떤 순서로 일하는지 듣고, 그 안에서 가장 자주 막히는 지점을 화면과 데이터 구조로 옮겼습니다. Akasys에서는 단순 요청 티켓 제품을 내부 티켓, 고객 요구사항, 주간/월간 리포트가 연결되는 운영 도구로 확장 제안했습니다.

React, Next.js 기반 화면 구현뿐 아니라 API 사용 방식, 상태 흐름, 모바일 레이아웃, 결제와 푸시 연동, 분석 이벤트까지 함께 다뤘습니다. 필요하면 NestJS, GraphQL, MongoDB 쪽 비즈니스 로직과 스키마도 직접 구현했습니다.

Founder lesson

OnTheMarket은 좋은 문제를 찾았지만, 제품만으로 풀 수 없는 비용이 컸습니다.

음식점주가 가격을 빨리 알고 싶어한다는 문제는 명확했고, 가격 진단 캠페인으로 일부 가입 전환도 만들었습니다. 다만 B2B 식자재 시장은 신뢰 확보, 공급가 경쟁력, 대면 영업, 공급 운영이 함께 돌아가야 했고 작은 팀이 감당하기엔 무거웠습니다. 그래서 제품의 완성도만큼 유통 구조와 영업 비용을 빨리 검증했어야 한다는 걸 배웠습니다.

점주가 원하는 문제는 있었지만, 그 문제를 반복 가능한 사업으로 만들려면 더 싼 공급가, 안정적인 물류/공급 운영, 대면 영업망이 같이 필요했습니다. 작은 팀이 제품 개발과 시장 운영을 동시에 감당하기에는 비용이 컸습니다.

문제를 끝까지 파고드는 일은 계속 좋아합니다. 다만 지금은 좋은 제품팀 안에서 더 큰 사용자 규모, 실험 문화, 협업 방식을 배우며 제품을 성장시키는 경험을 쌓고 싶습니다.

화면을 예쁘게 만드는 것보다 사용자가 가치를 언제 이해하는지가 더 중요하다는 걸 배웠습니다. 가격 진단 캠페인처럼 가입이나 주문 전에 절감 가능성을 먼저 보여주는 식으로, 화면의 정보 노출 순서를 제품 가설과 연결해 보게 됐습니다.

Collaboration

작은 팀에서도 역할과 요구사항을 계속 맞춰가며 만들었습니다.

2인 창업팀에서 OnTheMarket을 만들었고, Akasys를 맡겼던 AkanJS 쪽 개발자/대표와는 이후 SYRS, ChapterTwo, OnTheMarket 프레임워크 지원까지 계속 협업했습니다. 요구사항을 그대로 구현하기보다 상대 팀이 실제로 얻고 싶은 결과를 다시 정리하고, 화면과 데이터 구조로 합의하는 방식으로 협업해왔습니다.

구현 방식과 화면 흐름은 제가 주도한 경우가 많았지만, 문제 정의와 우선순위는 항상 고객, 공동창업자, 협업 개발자와 맞춰가며 정했습니다. 혼자 빠르게 만들되, 방향은 계속 확인하는 방식으로 일했습니다.

Akasys 프로젝트를 계기로 요구사항 정리와 구현 방식을 좋게 봐주셨고, 이후 SYRS, ChapterTwo, OnTheMarket까지 일이 이어졌습니다. OnTheMarket에서는 AkanJS 프레임워크를 쓰면서 실제 제품 개발 중 필요한 피드백과 적용을 함께 맞췄습니다.

처음부터 정답을 단정하기보다, 사용 맥락과 제약을 먼저 맞추고 작은 단위로 구현해 확인하는 편입니다. 특히 화면 문구, 상태 흐름, 데이터 구조가 서로 어긋나지 않게 계속 맞추는 일을 중요하게 봅니다.

Growth edges

빠른 실행력 뒤에, 더 배워야 할 협업 방식과 검증 과정이 있습니다.

작은 팀과 외주에서는 넓은 범위를 빠르게 책임지는 데 익숙해졌지만, 여러 직군과 개발자가 하나의 제품을 장기간 함께 성장시키는 경험은 상대적으로 적습니다. 또 해보고 싶은 아이디어가 생기면 시장조사나 사용자 인터뷰를 충분히 마치기 전에 개발부터 시작하는 편입니다. 빠르게 실행하며 배운 것도 많지만, 틀린 가설을 빠르게 구현하는 비용 역시 경험했습니다.

상대적으로 적은 것은 사실입니다. 대신 문제 정의부터 화면, API, 운영까지 전체 맥락을 맡아왔고, 고객, 공동창업자, 협업 개발자의 피드백을 빠르게 제품에 반영해왔습니다. 이제는 코드 리뷰, 문서화, 공동 의사결정이 더 촘촘한 환경에서 이 넓은 시야를 팀의 방식으로 확장하고 싶습니다.

무언가 가능해 보이면 시장조사와 사용자 인터뷰를 개발과 동시에 시작하는 경향이 있습니다. 덕분에 빠르게 실물을 보여줄 수 있지만, 실제 병목이 제품 밖의 영업, 유통, 운영에 있을 때는 잘못된 가설을 빠르게 구현하게 됩니다. OnTheMarket을 통해 제품보다 먼저 검증해야 할 조건이 있다는 것을 배웠습니다.

개발 전에 해결하려는 문제, 아직 모르는 가정, 확인할 사용자를 먼저 적고, 전체 기능보다 가장 작은 화면이나 프로토타입으로 반응을 확인하려 합니다. 계속할 기준과 멈출 기준도 미리 정해, 실행 속도를 줄이기보다 검증 순서를 앞당기는 쪽으로 보완하고 있습니다.

OnTheMarket · Solved issue 02 · 개선 이력 #33

결제 앱을 다녀온 뒤에도 같은 화면처럼

Capacitor WebView와 외부 PG·결제 앱 사이의 navigation을 플랫폼별로 분기하고, 내부 화면 복귀 시 native safe-area와 web viewport를 함께 복원한 작업입니다.

Problem & constraints

결제 왕복은 URL 이동이면서 동시에 WebView 레이아웃 상태 전환이었습니다.

자사 화면은 edge-to-edge와 CSS safe-area를 사용했지만 외부 PG 문서는 native 안전 영역이 필요했습니다. 카드사·은행 앱 호출만 처리하면, 복귀 뒤 외부 페이지의 inset과 오래된 viewport가 내부 화면에 남았습니다.

External page 외부 DOM의 CSS 계약에 의존할 수 없음

PG 문서는 WebView 컨테이너 바깥에서 안전 영역을 보장해야 했습니다.

Platform Android intent와 iOS scheme이 다름

Android의 intent·미설치 fallback과 iOS의 navigation delegate를 각각 다뤄야 했습니다.

Return redirect 완료 뒤 URL을 다시 판별

결제 결과 주소에 도착하는 것과 WebView의 레이아웃이 원상 복구되는 것은 별도 상태였습니다.

내부 주문→ 외부 PG→ OS 결제 앱→ PG redirect→ 내부 결과 route
success route /order/success

결제 인증이 성공하면 PG가 이동시키는 앱 내부 웹 주소입니다. 주문번호·결제키·금액을 서버에서 대조하고 Toss 승인 API를 호출한 뒤 결과 화면을 보여줍니다.

fail route /order/fail

실패 시 PG가 돌려보내는 앱 내부 웹 주소입니다. 기존 주문 품목을 장바구니 쿼리로 재구성해 재시도 화면으로 연결합니다.

두 주소는 카드·은행 앱을 여는 deep link가 아닙니다. 결제 시작 시 Toss SDK에 window.location.origin 기준의 “결과 반환 주소”로 등록했습니다. 이 결제 왕복에서 custom scheme·intent://는 외부 결제 앱 실행에 사용했습니다.

Observed before

복귀는 됐지만, 하단 내비게이션은 서로 반대 방향으로 깨졌습니다.

하나의 WebView가 내부 주문 화면과 제어할 수 없는 PG 문서를 번갈아 로드했습니다. 내부 화면은 웹이 safe-area를 계산하고 외부 문서는 native가 여백을 보장해야 했는데, 복귀 경계에서 그 소유권이 정확히 넘어오지 않았습니다.

왜 iOS reflow인가

.always를 .never로 바꾸고 inset을 0으로 만들어도, 이미 그려진 WKWebView의 visual viewport 높이·offset은 외부 문서 기준으로 남을 수 있었습니다. 높이를 0.1pt 변경했다 원복해 native layout을 무효화하고 window.resize를 전달한 뒤 다음 visualViewport 변화를 한 번 더 감지해 fixed·vh 기반 요소를 다시 배치했습니다.

Trade-off

최초·개선 진단 API의 최대 시도 횟수를 1회에서 5회로 늘리면 성공 기회는 커지지만, 최악의 경우 모델 호출 비용과 대기시간도 함께 커집니다. 그래서 재시도 정책을 화면의 대기·실패 상태와 함께 설계했습니다.
