Product translation

외주개발과 창업을 하며 다양한 요구사항을 소프트웨어로 옮겨왔습니다.

외주개발에서는 고객이 설명한 요구사항을 화면, API, 데이터 구조로 정리해 납품했고, 창업에서는 문제 발견부터 제품 구현, 영업, 운영, 지표 확인까지 직접 부딪혔습니다. 음식점 식자재 발주, AI 스킨케어 상담, 내부 운영 도구, 모바일 웹앱처럼 사용 맥락이 다른 제품을 만들었습니다.

외주는 상대가 이미 가진 불편함을 정리해 납품 가능한 형태로 만드는 일이었고, 창업은 문제가 맞는지부터 계속 검증해야 하는 일이었습니다. 창업을 하면서 기능보다 유통, 영업, 운영까지 함께 봐야 한다는 감각이 생겼습니다.

먼저 사용자가 실제로 어떤 순서로 일하는지 듣고, 그 안에서 가장 자주 막히는 지점을 화면과 데이터 구조로 옮겼습니다. Akasys에서는 단순 요청 티켓 제품을 내부 티켓, 고객 요구사항, 주간/월간 리포트가 연결되는 운영 도구로 확장 제안했습니다.

React, Next.js 기반 화면 구현뿐 아니라 API 사용 방식, 상태 흐름, 모바일 레이아웃, 결제와 푸시 연동, 분석 이벤트까지 함께 다뤘습니다. 필요하면 NestJS, GraphQL, MongoDB 쪽 비즈니스 로직과 스키마도 직접 구현했습니다.

Founder lesson

OnTheMarket은 좋은 문제를 찾았지만, 제품만으로 풀 수 없는 비용이 컸습니다.

음식점주가 가격을 빨리 알고 싶어한다는 문제는 명확했고, 가격 진단 캠페인으로 일부 가입 전환도 만들었습니다. 다만 B2B 식자재 시장은 신뢰 확보, 공급가 경쟁력, 대면 영업, 공급 운영이 함께 돌아가야 했고 작은 팀이 감당하기엔 무거웠습니다. 그래서 제품의 완성도만큼 유통 구조와 영업 비용을 빨리 검증했어야 한다는 걸 배웠습니다.

점주가 원하는 문제는 있었지만, 그 문제를 반복 가능한 사업으로 만들려면 더 싼 공급가, 안정적인 물류/공급 운영, 대면 영업망이 같이 필요했습니다. 작은 팀이 제품 개발과 시장 운영을 동시에 감당하기에는 비용이 컸습니다.

문제를 끝까지 파고드는 일은 계속 좋아합니다. 다만 OnTheMarket에서 사장님의 문제를 풀다가 제품 밖 유통·영업·신뢰가 병목이라는 걸 배웠기 때문에, 지금은 이미 그 기반을 가진 제품팀 안에서 같은 사용자의 문제를 더 큰 규모로 풀며 실험 문화와 협업 방식을 배우고 싶습니다.

화면을 예쁘게 만드는 것보다 사용자가 가치를 언제 이해하는지가 더 중요하다는 걸 배웠습니다. 가격 진단 캠페인처럼 가입이나 주문 전에 절감 가능성을 먼저 보여주는 식으로, 화면의 정보 노출 순서를 제품 가설과 연결해 보게 됐습니다.

Collaboration

작은 팀에서도 역할과 요구사항을 계속 맞춰가며 만들었습니다.

2인 창업팀에서 OnTheMarket을 만들었고, Akasys를 맡겼던 AkanJS 쪽 개발자/대표와는 이후 SYRS, ChapterTwo, OnTheMarket 프레임워크 지원까지 계속 협업했습니다. 요구사항을 그대로 구현하기보다 상대 팀이 실제로 얻고 싶은 결과를 다시 정리하고, 화면과 데이터 구조로 합의하는 방식으로 협업해왔습니다.

구현 방식과 화면 흐름은 제가 주도한 경우가 많았지만, 문제 정의와 우선순위는 항상 고객, 공동창업자, 협업 개발자와 맞춰가며 정했습니다. 혼자 빠르게 만들되, 방향은 계속 확인하는 방식으로 일했습니다.

Akasys 프로젝트를 계기로 요구사항 정리와 구현 방식을 좋게 봐주셨고, 이후 SYRS, ChapterTwo, OnTheMarket까지 일이 이어졌습니다. OnTheMarket에서는 AkanJS 프레임워크를 쓰면서 실제 제품 개발 중 필요한 피드백과 적용을 함께 맞췄습니다.

처음부터 정답을 단정하기보다, 사용 맥락과 제약을 먼저 맞추고 작은 단위로 구현해 확인하는 편입니다. 특히 화면 문구, 상태 흐름, 데이터 구조가 서로 어긋나지 않게 계속 맞추는 일을 중요하게 봅니다.

Growth edges

빠른 실행력 뒤에, 더 배워야 할 협업 방식과 검증 과정이 있습니다.

작은 팀과 외주에서는 넓은 범위를 빠르게 책임지는 데 익숙해졌지만, 여러 직군과 개발자가 하나의 제품을 장기간 함께 성장시키는 경험은 상대적으로 적습니다. 또 해보고 싶은 아이디어가 생기면 시장조사나 사용자 인터뷰를 충분히 마치기 전에 개발부터 시작하는 편입니다. 빠르게 실행하며 배운 것도 많지만, 틀린 가설을 빠르게 구현하는 비용 역시 경험했습니다.

상대적으로 적은 것은 사실입니다. 대신 문제 정의부터 화면, API, 운영까지 전체 맥락을 맡아왔고, 고객, 공동창업자, 협업 개발자의 피드백을 빠르게 제품에 반영해왔습니다. 회원 200명 규모 독서모임을 운영하며 온보딩 동선과 운영 규칙을 다듬어온 경험도 사람들과 합을 맞추는 감각의 바탕이 됐습니다. 이제는 코드 리뷰, 문서화, 공동 의사결정이 더 촘촘한 환경에서 이 넓은 시야를 팀의 방식으로 확장하고 싶습니다.

무언가 가능해 보이면 시장조사와 사용자 인터뷰를 개발과 동시에 시작하는 경향이 있습니다. 덕분에 빠르게 실물을 보여줄 수 있지만, 실제 병목이 제품 밖의 영업, 유통, 운영에 있을 때는 잘못된 가설을 빠르게 구현하게 됩니다. OnTheMarket을 통해 제품보다 먼저 검증해야 할 조건이 있다는 것을 배웠습니다.

개발 전에 해결하려는 문제, 아직 모르는 가정, 확인할 사용자를 먼저 적고, 전체 기능보다 가장 작은 화면이나 프로토타입으로 반응을 확인하려 합니다. 계속할 기준과 멈출 기준도 미리 정해, 실행 속도를 줄이기보다 검증 순서를 앞당기는 쪽으로 보완하고 있습니다.

OnTheMarket · Solved issue 04

장부·상품 서비스의 순환 의존 해소

견적 요청 기능을 붙이면서 장부·상품·식당 서비스 사이에 DI 순환이 생겼고, 두 서비스에 걸치는 작업을 resolver 계층에서 두 호출로 분리해 의존 방향을 장부 → 유통사·식당 한쪽으로 정리한 작업입니다.

Problem & constraints

장부 서비스가 유통사·식당 서비스를 새로 필요로 하게 됐습니다.

온더마켓은 음식점 점주가 식자재 유통사를 비교해 주문하는 B2B 서비스입니다. 점주는 매번 비슷한 식자재를 반복해서 사기 때문에, 자주 사는 품목을 장부(Ledger)에 저장해 두고 그 목록을 기준으로 유통사 가격 비교·주문·견적 요청을 시작하는 구조로 만들었습니다. 이 사례에 얽힌 모델은 아래 여섯 개입니다.

Restaurant 음식점
점주의 매장. 사업자·주소·배송 시간대·수령 방식·전화번호를 갖고, 보유 장부 id 배열 ledgers[]와 즐겨찾는 유통사 favoriteDistributors[]를 들고 있습니다. 알림톡의 수신 번호와 식당명이 여기서 나옵니다.
Distributor 유통사
식자재 공급사. 사업자·정산 계좌·토스 셀러 정보와 함께 상품별 가격표 pricingCatalogs[](catalog·costPrice·sellingPrice·date)를 갖습니다. 최저가 계산 listInPriceRank는 이 가격표를 장부 품목에 대입해 총액 순으로 정렬합니다.
Catalog 상품 마스터
이름·단위·규격·masterCode·status(active/master/inactive)를 가진 상품 원장. 장부 품목, 주문 품목, 유통사 가격표가 모두 이 id를 참조하므로, 상품을 비활성화하면 참조를 함께 정리해야 합니다.
Ledger 장부
restaurantId·name·lineItems[](catalog·quantity·unitPrice)·status(active/quote/closed/shared). 품목 추가·제거·수정 API와 장바구니 URI 변환이 붙어 있어, 점주가 반복 주문할 품목 리스트이자 유통사 비교의 출발점으로 쓰였습니다.
BidTicket 입찰권
distributorId와 restaurant의 쌍. 유통사가 "이 식당에 공급하겠다"고 등록한 기록이고, 견적 요청에서는 한 식당에 몇 곳의 유통사가 입찰했는지 세는 단위입니다.
Order 주문
장부에서 고른 lineItems[]가 특정 distributor·배송일·총액과 함께 확정된 기록. 결제 승인은 PG(토스페이먼츠)가 처리하고, 서버는 결과 상태만 받아 적습니다.

2025년 11월에 붙인 견적 요청 기능은, 점주가 장부를 status: "quote"로 올리면 유통사들이 BidTicket으로 입찰하고, 매일 저녁 배치(@Schedule.Cron)가 입찰 수가 threshold(3) 이상인 음식점에 최저가 유통사와 가격을 카카오 알림톡으로 보내는 흐름입니다. 최저가는 DistributorService.listInPriceRank, 전화번호와 식당명은 RestaurantService가 갖고 있었으므로, 배치를 담는 LedgerService가 이 두 서비스를 주입받아야 했습니다.

Observed before

상품·식당 서비스가 이미 장부 서비스를 보고 있어 순환이 생겼습니다.

기존 관계는 세 갈래였습니다. RestaurantService는 식당 생성 시 기본 장부를 만들고 그 id를 restaurant.ledgers에 넣으려고(initLedger) LedgerService를 주입받았고, CatalogService는 상품 비활성화 시 모든 장부의 lineItems에서 그 상품을 지우려고(removeAllLineItemsByCatalogId) 역시 LedgerService를 주입받았습니다. DistributorService는 가격표 갱신과 입찰 처리를 위해 원래부터 CatalogService·RestaurantService·BidTicketService에 의존했습니다. 모델 레벨에서는 Restaurant가 장부 id를 들고 있어 방향이 Restaurant → Ledger 한쪽이었지만, 서비스 레벨에서는 LedgerService에 새 의존을 더하는 순간 DI 그래프가 두 곳에서 돌기 시작했습니다.

DistributorService→ CatalogService→ LedgerService→ DistributorService↺ 순환
RestaurantService→ LedgerService→ RestaurantService↺ 순환

Solution

상품·식당 서비스에서 장부 의존을 빼고, 걸치는 작업은 Signal에서 두 번 호출했습니다.

장부는 식당·유통사·상품을 알아야 하지만 그 반대는 아니어도 된다고 보고, 의존 방향을 장부 → 유통사·식당 한쪽으로만 두기로 했습니다. CatalogService.inactivateCatalog는 상품 상태만 바꾸고, 장부에서 품목을 지우는 호출은 GraphQL resolver인 catalog.signal.ts가 이어서 하도록 옮겼습니다. initLedger는 RestaurantService에서 LedgerService로 옮겨 장부를 만든 뒤 restaurantService로 식당의 ledgers를 갱신하게 했고, restaurant.signal.ts가 ledgerService.initLedger를 부르게 했습니다.

LedgerService→ DistributorService· RestaurantService단방향 · Catalog·Restaurant는 Ledger를 모름
01 · 의존 제거Catalog · Restaurant에서 @Srv() ledgerService 삭제
→
02 · 책임 이동initLedger를 LedgerService로
→
03 · 조합 지점Signal이 두 서비스를 순서대로 호출

Code change

서비스 안에서 이어지던 두 작업을 resolver의 두 줄로 나눴습니다.

Beforecatalog.service.ts가 ledgerService를 직접 호출
@Service("CatalogService")
export class CatalogService extends DbService(db.catalogDb) {
  @Srv() ledgerService: srv.LedgerService;

  async inactivateCatalog(catalogId: string) {
    const catalog = await this.getCatalog(catalogId);
    await catalog.set({ status: "inactive" }).save();
    await this.ledgerService
      .removeAllLineItemsByCatalogId(catalogId);
  }
}
Aftercatalog.signal.ts에서 두 서비스를 차례로 호출
// catalog.signal.ts
@Mutation.Admin(() => Boolean)
async inactivateCatalog(
  @Arg.Body("catalogId", () => String) catalogId: string
) {
  await this.catalogService.inactivateCatalog(catalogId);
  await this.ledgerService
    .removeAllLineItemsByCatalogId(catalogId);
  return true;
}

// ledger.service.ts
@Srv() distributorService: srv.DistributorService;
@Srv() restaurantService: srv.RestaurantService;

한 달 뒤 후속 커밋에서는 createRestaurant 직후에도 ledgerService.initLedger(restaurant.id)를 호출하도록 보완해, 첫 장부 목록 조회 전에도 기본 장부가 생기도록 했습니다.

Outcome & trade-off

순환은 사라졌지만, 두 호출 사이의 원자성은 포기했습니다.

Outcome Ledger → Distributor · Restaurant 단방향

견적 요청·입찰 알림 배치를 LedgerService 안에 두고도 DI 순환 없이 서버가 뜨게 됐습니다. Catalog·Restaurant 서비스는 장부의 존재를 모릅니다.

Trade-off 상품 비활성 후 장부 정리 실패 가능

첫 호출은 성공하고 두 번째가 실패하면 상품은 비활성인데 장부에는 품목이 남는 중간 상태가 생깁니다. 트랜잭션이나 보상 로직은 두지 않았습니다.

원자성을 일단 포기해도 된다고 판단한 근거는 이 흐름에 현금이 오가지 않는다는 점이었습니다. 결제 승인과 취소는 PG가 처리하고, 여기서 끊기는 것은 상품 상태와 장부 품목 정리뿐이라 중간 상태가 남아도 돈이 잘못 움직이지는 않습니다. 덧붙여 상품 비활성화는 관리자가 드물게 수행하는 작업이라 다음 정리 호출로 회복할 수 있었고, 1인 개발에서는 기능을 먼저 내보내는 속도가 우선이었습니다. 호출 빈도가 늘어나면 두 호출을 하나의 트랜잭션으로 묶거나 실패 시 재실행할 수 있는 정리 배치를 두는 것이 다음 단계입니다.

OnTheMarket · Solved issue 02

주문 목록의 데이터 깊이를 다시 설계하다

점주 화면에서 10초 가까이 걸리던 주문 목록 조회를, 관계 데이터의 의존 관계를 정리하고 목록·중첩 관계에 Light 모델 경계를 세워 눈에 띄게 빠르게 만든 작업입니다.

Problem & constraints

음식점 주문 목록 화면이 뜨는 데 10초 정도씩 걸렸습니다.

점주가 앱에서 주문 내역 탭을 열면 목록이 뜨기까지 10초 가까이 기다려야 했습니다. 주문 카드는 판매자명·연락처·납품서용 사업자 정보를 바로 보여줘야 했으므로, 주문(Order)이 유통사·식당 데이터를 필드로 들고 있는 구조 자체는 유지해야 했고, 단건 상세 화면이 쓰는 Full 모델도 건드릴 수 없었습니다.

Observed before

관계 필드가 자동으로 전부 조회되면서 가격표와 이미지 메타데이터까지 따라왔습니다.

1인 개발 편의상 akanjs의 resolver와 자동 fragment가 관계 필드를 id로 알아서 조회해 전부 내려주도록 두고 있었습니다. 목록 20건마다 유통사 Full 모델이 붙고, 그 안의 상품별 가격표 약 100개가 Catalog와 image 메타데이터까지 연쇄로 따라오면서 서버가 받아 오는 데이터가 너무 많아졌습니다.

List query LightOrder[] · 기본 20건
Full relation Distributor
↓
유통사별 약 100개 pricingCatalogs[] costPrice · sellingPrice · date + Catalog 도메인 필드 8개
↓
각 가격 항목마다 Catalog → image → File metadata 상품명·단위·규격·상태 뒤에, 이미지가 있으면 파일명·MIME·URL·가로/세로·용량 등 11개 메타 필드로 확장

확인한 운영 데이터 구조 20 orders × 100 prices = 직접 유통사 경로에서 최대 2,000개 가격 객체 반복 가능

과거 로그의 가격표 블록 33개가 모두 100개 항목이었고, 주문 목록의 기본 page size는 20이었습니다.

Solution

데이터 의존 관계를 그려 보고, 목록에 필요한 필드와 아닌 필드를 나눴습니다.

Order → Distributor → PricingCatalog → Catalog → image로 이어지는 관계 그래프를 따라가며 목록이 실제로 읽는 값을 표시했습니다. 판매자명·연락처·사업자번호·표시 주소처럼 카드와 납품서에 쓰는 값은 남기고, 상품별 가격표·정산 계좌·PG 입점 상태처럼 가격 관리나 설정 화면에서만 쓰는 값은 뺐습니다.

경계

akanjs는 배열 조회에 Light, 단건 조회에 Full 모델로 fragment를 만듭니다. 목록과 중첩 관계는 LightDistributor·LightRestaurant·LightLedger로 경계를 세우고, 단건 상세는 Full을 유지했습니다.

결제 앱을 다녀온 뒤에도 같은 화면처럼

외부 결제사(PG) 페이지를 웹뷰 안에서 오가면서 생긴 inset 문제를 한 단계씩 좁혀 간 작업입니다. 외부 페이지에서는 native가 inset을 대신 맞춰주고, 내부 화면으로 돌아오면 웹 레이아웃이 safe-area와 viewport를 다시 재도록 만들었습니다.

Problem & constraints

결제는 우리가 제어할 수 없는 외부 페이지를 웹뷰 안에서 다녀와야 했습니다.

앱 안에서 결제를 하려면 TossPayments 같은 외부 결제사(PG) 페이지를 거쳐야 했습니다. 우리가 직접 손댈 수 없는 문서입니다. 팝업이나 별도 앱·브라우저로 나갔다가 다시 돌아오는 방식은, 휴대폰에 시간을 많이 쓰고 싶어 하지 않고 연령대가 꽤 있는 식당 점주들에게 어렵다고 판단했습니다. 그래서 다른 앱으로 내보내는 리다이렉트를 최소화하고, 웹뷰 안에서 실제 URL을 바꿔 PG 페이지로 갔다가 돌아오는 플로우를 택했습니다.

기존 웹앱 구조는 웹페이지와 앱을 같은 코드로 운영하기 위해 휴대폰 화면 전체를 웹뷰로 덮고, 노치·홈 인디케이터 같은 safe-area(inset)는 Capacitor로 감지해 CSS 값으로 웹 레이아웃에 넘겨주는 방식이었습니다. 내부 화면에서는 웹이 safe-area를 소유했습니다.

외부 PG 페이지에서는 이 방법을 쓸 수 없었습니다. 우리 CSS가 없는 문서라 native 단에서 WebView의 inset을 직접 다뤄야 했고, 그 과정에서 아래 문제들이 순서대로 나타났습니다.

Observed before

스트림은 정상 종료됐는데 제품이 쓸 수 없는 응답이 반복됐습니다.

실제로 관찰된 실패는 세 가지였습니다. JSON 앞뒤에 "다음은 분석 결과입니다" 같은 설명 문장이 붙어 JSON.parse가 바로 실패하는 경우, 파싱은 되지만 skinAge나 oilWaterBalanceDesc 같은 필수 분석 필드가 빠진 경우, 그리고 고객이 고른 언어와 다른 언어로 응답하는 경우였습니다. 세 경우 모두 서버에서는 정상 응답으로 보였기 때문에, 이 상태로는 결과를 저장하거나 화면에 그릴 수 없었습니다.

Solution

프롬프트의 기대를 런타임 성공 조건으로 옮기고, 실패하면 다시 호출했습니다.

스트림으로 모은 출력에서 첫 {와 마지막 } 사이만 잘라 파싱하고, 최초 진단은 isSkinData, 개선 진단은 isSkinImprovementData 타입 가드로 필수 필드와 값 타입을 검사했습니다. 가드를 통과하지 못하면 정상 결과로 저장하지 않고 오류로 던져 최대 5회까지 다시 시도했고, 개선 진단 프롬프트에는 선택 언어를 다시 명시해 언어 불일치를 줄였습니다.

Outcome & trade-off

포맷은 런타임에서 보장됐고, 길어진 대기는 애니메이션으로 흡수했습니다.

검증을 통과한 응답만 저장되므로 화면이 깨진 결과를 받는 일은 사라졌습니다. 대신 재시도 때문에 최악의 경우 대기시간과 호출 비용이 시도 횟수만큼 늘어나는 트레이드오프가 생겼습니다. 이 시간을 더 줄이는 대신 제품 경험 안에 넣기로 했습니다. 최초 진단용 Loading과 개선 진단용 SolutionLoading에 react-spring 스캔 애니메이션을 두어 기다리는 동안 분석이 진행 중이라는 느낌을 주고, 영·한·일·태 4개 언어 안내와 닫기·처음으로 돌아가기 오류 복구 동선을 연결했습니다. 개선 진단은 최초 진단의 OpenAI 스레드를 이어받아 이전 결과를 비교 맥락으로 사용합니다.

Trade-off

5회는 항상 호출하는 횟수가 아니라 실패했을 때 쓸 수 있는 상한입니다. 그래도 최악의 경우 대기와 비용은 커지므로, 그 시간을 사용자가 견딜 수 있게 만드는 로딩 화면까지가 이 작업의 범위였습니다.

LLM 응답은 호출이 성공한 것이 아니라 검증을 통과한 것이어야 제품이 쓸 수 있습니다. 검증이 만드는 시간은 숨길 수 없으니, 그 시간을 어떻게 보여줄지까지가 기능의 일부였습니다.

function isSkinData(data): data is SkinData {
  if (
    typeof data === "object" &&
    data !== null &&
    "overview" in data &&
    "skinAge" in data &&
    "skinAgingDesc" in data &&
    "sensitivityDesc" in data &&
    "oilWaterBalanceDesc" in data &&
    "type" in data
  ) {
    return (
      typeof data.overview === "string" &&
      typeof data.skinAge === "number" &&
      typeof data.skinAgingDesc === "string" &&
      typeof data.sensitivityDesc === "string" &&
      typeof data.oilWaterBalanceDesc === "string" &&
      (data.type === "typeA" || data.type === "typeB" ||
        data.type === "typeC" || data.type === "typeD" ||
        data.type === "typeE")
    );
  }
  return false;
}

개선 진단용 isSkinImprovementData는 여기에 노화·민감도·유수분 개선 설명 3개 필드를 추가로 요구하는 별도 가드입니다. HTTP 성공이 아니라 이 가드를 통과해야 진단 성공으로 저장됩니다.

스트림 수집·JSON 추출·오류 분류 — threadId를 남기는 실패 경로 코드 보기 
const run = openai.beta.threads.runs
  .stream(thread.id, { assistant_id: prompt.assistantId })
  .on("textDelta", (textDelta) => {
    if (!textDelta.value) return;
    outputParts.push(textDelta.value);
  })
  .on("error", (e) => {
    reject(errors.apiError(e.message, thread.id));
  })
  .on("end", () => {
    const outputText = outputParts.join("");
    // 설명 문장이 붙은 응답에서 JSON 구간만 추출
    const jsonStart = outputText.indexOf("{");
    const jsonEnd = outputText.lastIndexOf("}") + 1;
    /* … 파싱 실패 시 errors.unknownError(…, thread.id) reject … */
    const jsonObject: unknown = JSON.parse(outputText.slice(jsonStart, jsonEnd));

    if (!isSkinData(jsonObject)) {
      reject(errors.jsonParseError("JSON parsing failed. …", thread.id));
    } else {
      jsonObject.threadId = thread.id;
      resolve({ skinData: jsonObject, rawResponse: outputText, threadId: thread.id });
    }
  });

오류를 apiError · jsonParseError · unknownError로 분류하고 모든 오류 메시지에 threadId를 실어 사후 추적이 가능하게 했습니다.
